# Experimental Touch Bar brightness menu

This prototype adds a menu for the **Touch Bar display itself**. It uses undocumented CoreBrightness and DFRBrightness APIs. The app does not disable system auto brightness, change display/sleep settings, or continuously keep the Touch Bar on. Selecting a level makes one request only on slider release; macOS may change it again. “Leave to system” sends no write and may not immediately undo the previous value.

A short-lived ARM helper checks its parent PID, exact Objective-C method encodings, the display ID and type 3, and a finite 5–100% range. Its only setter writes `DisplayBrightness` with a dictionary containing `Brightness`, `Commit: false`, and `CommitType: 0`; it never writes `DisplayBrightnessAuto`. See TouchBarFloor, which describes this private request as transient: https://github.com/volpierre/TouchBarFloor/blob/main/tbfloor.m. Apple does not document these semantics. No promise is made that they remain transient, that the display will accept a value, or that the request can be undone. A local M1/macOS 27.2 trial confirmed that a small user-initiated adjustment changed the Touch Bar brightness. Long-term behavior and OS overrides remain unverified.

The helper is a separate process with one operation in flight and a two-second deadline. The app blocks further brightness operations after a timeout because the request might have already been accepted: the result is unknown, not a confirmed failure. Timeout and quit send SIGTERM and escalate to SIGKILL if the child remains alive; the helper also watches its parent and exits if the parent dies. A process kill cannot undo a request already accepted by the system; a crash between the helper's parent check and the private call cannot be entirely excluded. No automatic replay or rollback is attempted. This helper is compiled as an ARM executable into the application bundle by `TouchBarHelper/build.sh`; the app and helper have not been Developer-ID signed or notarized.

Read-only discovery and one user-initiated brightness adjustment succeeded on an M1/macOS 27.2. Automated tests use a fake process or pure values and never modify Touch Bar settings. Payload tests check finite values, 5–100% boundaries, and that no auto-brightness field is written. Menu tests check that creating/opening the menu, selecting system mode, and quitting produce no device write, and a simulated slider release sends one write. Process tests cover success, failure, single in-flight, timeout, ignored late results, stopping, SIGTERM-resistant fake helper cleanup and child exit after parent SIGKILL.

Manual brighter settings can use more power and accelerate OLED wear; no specific effect is guaranteed. For a physical-device test, retain the prior working app and configuration, keep the original method available, choose a small intermediate change, check the actual display and reported value, then select system mode and watch whether macOS resumes automatic brightness. Do not test while display is locked/asleep. This is an experimental development build, not a release.
